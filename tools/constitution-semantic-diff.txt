# constitution-semantic-diff.txt — semantic rewrite manifest for the
# current release
#
# Purpose: the mechanical evidence required by §21.1 "生效范围" condition ③ —
# after every applicability marker is stripped from the Chinese text of the
# release under test, the result may differ from the previous release (v3.2.1)
# only inside the ranges declared below.  Read by
# tools/check_constitution_text.sh (check C5).
#
# Coordinates: **previous-release line numbers** (the v3.2.1 zh-CN file), not
# the current-release numbers — a declared range says "this part of the old
# text was deliberately rewritten", which stays meaningful after the new file
# grew.
#
# Strip rule used to produce the comparison (do not widen it):
#   1. delete a marker at the END of a line:      s/[ \t]*〔[^〕]*〕[ \t]*$//
#   2. delete a line that is ONLY a marker:       /^[ \t]*〔[^〕]*〕[ \t]*$/
# Never a global 〔〕 deletion: inline examples in the §21.1 syntax paragraph
# (and similar prose) are clause text, not markers.  The same rule is applied
# to BOTH editions, the previous release included: stripping one side only
# turns that side's own markers into phantom differences.
#
# Format:  <ids>  <start>-<end>  <anchor + why>
#   ids     : the modification point(s) of the revision plan that own this
#             range — M<n> a planned change, F<n> a fix from the final-text
#             review round, M0 a non-semantic change (version string only),
#             R<n> a range whose only justification is diff realignment — an
#             insertion that re-split hunks already owned by another range —
#             never a rewording.
#   range   : previous-release lines, inclusive, 1-based.
#
# Change records answer a different question — "what did this release change?" —
# and are verified positively instead of by hunk coverage.  Coverage alone cannot
# say "this section is new here": a hunk is the finest granularity the range
# model has, so an inserted section that abuts a rewritten paragraph shares that
# hunk under any diff alignment.  Records are in NEW-edition coordinates:
#   Format:  <N|X><n>  <line>  <anchor>  — <what changed>
#     N<n> : a clause this release ADDS — <line> must be a heading.
#     X<n> : a line this release REVISES — <line> must not be a heading.
#     <line>   : line number in the published Chinese edition of this release.
#     <anchor> : a distinctive substring of that line.  The check requires it to
#                sit on <line>, to be scope-unique (N: the only *heading*
#                containing it; X: the only *line* containing it), and requires
#                the whole line NOT to occur verbatim in PREV_TAG after the
#                marker strip — an unchanged line is not a change.  A wrong
#                <line> therefore FAILS instead of passing quietly.
#
# Notes:
#   * Markers are metadata: they vanish under the strip rule, so they can never
#     justify a textual difference — no marker-only edit needs a range or a
#     record.
#   * Records are verified on every run, including a run whose diff is empty:
#     an empty diff says nothing about whether the records are right.
#   * A MOVE is declared as two ranges and needs no record of its own: the
#     source hunk (a deletion) and the destination hunk (a zero-width
#     insertion).  Neither the clause nor its text is new, so an N record would
#     lie and an X record would fail by construction (the moved lines do occur
#     verbatim in PREV_TAG).  R<n> does not apply either: it covers diff
#     realignment, not a deliberate relocation.
#
# Declarations for v4.0.0 → v4.1.0. The v3.2.1-era declarations were retired
# together with their base (they addressed v3.2.1 line numbers and would have
# authorized any hunk inside them). Coordinates below are **v4.0.0** lines.

# ── Why the thresholds cannot be replaced by qualitative wording (exception 4,
#    clause four of the "criterion thresholds" exception).
#
#    §12.5 states three numbers: 200 characters per comment, at most 2 lines,
#    and line comments at most 5% of a code line count. Deleting any of them
#    leaves "keep comments short" / "keep comments rare" — a criterion nobody
#    can judge, which is worse than a strict number: every reader then applies
#    their own standard and the clause stops being one rule (§1.4).
#
#    Why these three and not others:
#    200 characters is the length at which a comment still fits one terminal
#    line at a normal width; beyond it the reader starts wrapping, and a
#    wrapped comment is where multi-paragraph essays begin. 2 lines is the same
#    bound stated in lines so a narrow editor cannot smuggle a longer comment.
#    5% is the share at which comments stop being annotations and become a
#    parallel narrative: measured on this repository's own modules, healthy
#    files sit near 5% (user-ledger 4.8%, compaction 5.1%) while the runaway
#    files in the consumer project that motivated this clause sat at 21-49%.
#    The gap is wide, so the threshold is not a knife edge.
#
#    Fourth threshold (same record): a file whose comments total fewer than 200
#    characters is exempt from the ratio item. Deleting it would make every
#    tiny file violate the 5% cap on arithmetic grounds alone (30 code lines x
#    5% = 1.5 lines, so a single explanatory comment could fail the file), and
#    "small file" cannot be expressed qualitatively without putting a number
#    back somewhere. It is a floor on the measurement, not a second pass line.

#    Assumption to revisit: if a project shows a legitimate 8-10% ratio (dense
#    math, wire-format tables), that is evidence for raising the number, not
#    for deleting it — the amendment path is a threshold change with its own
#    record, not a return to "keep it low".
